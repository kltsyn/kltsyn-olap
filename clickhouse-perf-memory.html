ClickHouse 高性能怎么记

按「一句总纲 + 一条例子 + 三层人话 + 别记错」来记。不要背 18 条术语。

总纲 贯穿例子 文件结构 存储：少读+顺读 查询：批算 框架：别挡 口诀对照 自测

总纲

ClickHouse 快，是因为分析查询 少读、顺读、批算、别挡：只碰需要的列和数据段，磁盘顺序扫，CPU 按列块用 SIMD 算，并且不为行级事务买单。

少读只碰需要的列和数据段 顺读磁盘按排序键顺序扫 批算CPU 按列块用 SIMD 算 别挡不为行级事务买单

贯穿例子：搬书 vs 剪报

表 ads_click 有 80 列、每天几十亿行。查询只要：昨天、某广告位、计划 99、sum(fee)。后面五步、少读四张、跳数细图，都用这一句。

SELECT sum(fee)
FROM ads_click
WHERE date = yesterday()
  AND slot_id = 1001
  AND campaign_id = 99

数据实际走的五步：

查询时谁会被用到

.idx 不是每列一份，查询也不会把表上全部 .idx 一次性读进内存。80 列里绝大多数根本没有 .idx，只有 .bin 和 .mrk2。

真正叫 idx 的只有三类，而且按本句 SQL 选用：

文件磁盘上有几份本句 SQL 会不会用
primary.idx 每个 part 一份，只记 ORDER BY（date, slot）的 granule 边界，不是 80 列各一份 扫描这个 part 时会按需读取/利用。可能已在缓存里；新版本也可能流式读，不保证一次性整份载入。WHERE 带 date/slot 时用它扔叠
skp_idx_idx_campaign.idx 因为建了 INDEX idx_campaign，每个 part 一份 按需读取/利用（可能走缓存）。WHERE 有 campaign_id = 99，对得上
skp_idx_idx_user.idx 因为建了 INDEX idx_user，每个 part 一份 不读。本句 SQL 没有 user_id，这份布隆闲着
minmax_date.idx 分区键自动生成，每个 part 一份 分区表达式的 part 级 min/max，可参与 part/partition pruning。不是用户定义的跳数 INDEX
其余列 没有 .idx 无从读 idx。需要读数据时才打开对应列的 .bin / .mrk2

一句话：查询会按需读取/利用「这个 part 的主键目录」加上「本句 WHERE 用得上的跳数索引」。可能走缓存，新版本也可能流式读索引，不保证一次性把小文件完整载入。不是全部列，也不是表上声明过的全部 INDEX。

对上面那句 SQL，读路径如下。

磁盘上完整文件结构

MergeTree 不把一张表收成一个大文件。表目录里是许多不可变 part；每个 part 是一个文件夹。上面说的 primary.idx、skp_idx_*.idx、列 .bin 都在这个文件夹里。默认数据根目录是 /var/lib/clickhouse（Windows / 改过配置则看 path）。

下面打开昨天的一个 wide part（列多、行够多、默认自适应粒度）：每列一对 .bin + .mrk2。行数或体积不够时收成 compact part：同时看 min_bytes_for_wide_part 和 min_rows_for_wide_part 等，不是只看字节。compact 是一份 data.bin + data.mrk3，角色相同。关自适应粒度时标记文件是 .mrk 不是 .mrk2。

data/default/ads_click/20261011_1_1_0/
├── checksums.txt                 各文件校验
├── columns.txt                   本 part 有哪些列
├── count.txt                     行数
├── default_compression_codec.txt 默认压缩算法
├── metadata_version.txt          较新版本常见
├── serialization.json            较新版本：列序列化版本
├── partition.dat                 这个 part 的分区值
├── minmax_date.idx               分区表达式用到的列，在本 part 内的 min/max
├── primary.idx                   稀疏主键目录（ORDER BY 边界值）
├── date.bin / date.mrk2
├── slot_id.bin / slot_id.mrk2
├── campaign_id.bin / campaign_id.mrk2
├── fee.bin / fee.mrk2
├── … 其余 76 列各一对 .bin + .mrk2
├── skp_idx_idx_campaign.idx      跳数 INDEX 名 idx_campaign → 文件前缀 skp_idx_
├── skp_idx_idx_campaign.mrk2
├── skp_idx_idx_user.idx          跳数 INDEX 名 idx_user
└── skp_idx_idx_user.mrk2
文件角色查询时
ads_click.sql 表定义（列、ORDER BY、PARTITION、INDEX） 不读数据
part 文件夹名 分区 + 块号 + merge 层级 先按分区扔掉整天的文件夹
minmax_date.idx 分区表达式涉及列在本 part 内的 min/max，自动生成 辅助跳过整个 part（尤其范围条件）。砍整天主要靠文件夹名 / partition.dat。不是 INDEX TYPE minmax
primary.idx 稀疏主键，默认约每 8192 行一个排序键标记（自适应还看字节上限） 按需读取/利用（常被缓存，不保证一次性整份载入），二分找叠
skp_idx_idx_*.idx 跳数索引便利贴（名字 = skp_idx_ + INDEX 名） 按需读取/利用本句 WHERE 对得上的那几份，再扔叠。GRANULARITY N 覆盖 N 个 marks
*.mrk2 每一叠在对应 .bin 里的偏移 小文件，用来 seek 到那一叠
列.bin 该列压缩数据，按 granule 切块 只打开需要的列、没被扔掉的叠
checksums.txt 等 完整性、列清单、行数、压缩设置 读 part 时核对，不是过滤条件

别记错 · minmax_date.idx ≠ 用户定义的跳数 INDEX。 它是分区表达式的 part 级 min/max，可参与 part/partition pruning（尤其范围条件），不要当成完全不用这份文件。砍整天的文件夹，还会看 part 名和 partition.dat。INDEX idx_campaign TYPE minmax 才写成 skp_idx_idx_campaign.idx，用来扔掉 granule。

同一套文件还可能出现：可空列额外的 .null.bin；projections/；mutation 临时目录；detached/。较新版本可能把多份跳数索引收成 skp_idx.packed。ReplicatedMergeTree 副本协调在 ZooKeeper，磁盘上仍然是这些 part 文件夹。

上面是这一句查询怎么走，以及它在磁盘上对应哪些文件。下面按口诀拆零件：先少读、再顺读。不是把五步再讲一遍。

存储层：少读 + 顺读

这一层两件事：少碰磁盘，以及碰到的字节要连续。六张不是每张都「既少读又顺读」——先四张少读，再两张顺读。

少读：少打开列，少打开叠

左边是目录，右边是便利贴。二者都按块少扫，但不是同一种索引；右边里的 minmax/布隆也不等于跳数索引本身。跳数索引的一张贴覆盖几个 marks，看 GRANULARITY N。

别记错 · 跳数索引 ≠ minmax/布隆。 跳数索引是总称；minmax/布隆是其中两种贴法。稀疏主键也在跳 granule，但它是目录，不是跳数索引。主键裁剪以 granule 为单位；跳数索引由 INDEX … GRANULARITY N 决定一张贴覆盖几个 marks，N=1 才近似一叠。收益高度依赖数据相关性和查询谓词。

顺读：碰到的字节要连续

少读决定打开哪几叠；顺读决定这几叠在盘上是一段还是东一块西一块。

别记错 · 不是「彻底没有随机 I/O」。定位 granule 仍有 seek；快是因为命中后是大块顺序扫。

查询层：批算（附查询侧少读）

列块进内存之后，主业是批算。谓词下推是查询侧的少读，不算 SIMD；物化是预先批算好，看板改读小表。

别记错 ·「零拷贝」不是 ClickHouse 的正式术语。 更准确是：尽量按列块处理，避免物化为行对象。不必记成 Linux sendfile。

框架层：别挡

分析优先。INSERT 与 SELECT 不按行互锁，所以不太互堵；后台 merge、mutation、磁盘/CPU/内存竞争仍会造成资源争用。复杂事务、外键、频繁改一行，都不是它要优化的路径。

别挡C++ 自管内存

无 JVM GC 停顿。扫表热点路径少锁。后台 merge、mutation 仍会和查询抢 CPU/磁盘/内存。

别挡分片加算力、副本保活

数据本地算。跨分片 JOIN 要把行拉来拉去，弱，所以爱宽表。

别挡更新很贵

传统 ALTER … UPDATE mutation 通常重写受影响的 data parts，并非必然重写整张表。轻量更新/删除后来都有，但不是行级 OLTP。

别记错 · 不是「多进程模型」。主形态是单进程 clickhouse-server + 线程池，不是 PostgreSQL 那种一个连接一个进程。

别记错 · 插入原子、轻量删除/更新后来都有，但不是行级 OLTP。 传统 mutation 贵在重写受影响 part；记成「分析优先、更新很贵」。

口诀对照

口诀层条目
少读存储为主列存、压缩、稀疏主键、跳数索引；查询侧还有谓词下推
顺读存储追加 part、后台 merge、ORDER BY

自测

能用自己的话答完这五句，原文条目就可以不背。点开对一下。

1. 80 列只查 4 列为什么快一个数量级？

列存：每列一个文件，本句打开 date / slot / campaign / fee，不碰另外 76 列。同列再压缩，读盘字节更少。行式「即使只要 fee 也得搬整行」是教学概括；带覆盖索引的行存可能不必回表读完整行。

2. INSERT 为什么不原地改文件？merge 干什么？

MergeTree 记流水账：INSERT 只追加不可变 part，查询读已经写完的文件。INSERT 与 SELECT 不按行互锁，但仍会和后台 merge、mutation 抢磁盘/CPU/内存。后台 merge 把小文件装订成大文件，减少文件数，让顺序扫更顺。传统 ALTER UPDATE mutation 通常重写受影响 part，不是必然整张表。

3. 稀疏索引和 MySQL 主键 B+Tree 差在哪？

稀疏主键是章节目录，默认约每 8192 行一个标记（启用自适应粒度时还受 index_granularity_bytes 影响），文件是 primary.idx。查询会按需读取/利用这份目录和 WHERE 对得上的跳数索引，可能走缓存，不保证一次性整份载入。跳数索引由 INDEX GRANULARITY N 决定一张贴覆盖几个 marks，N=1 才近似一叠。二者都不是 80 列、也不是整表。定位到还要读的块之后，只解压那些叠上需要的列。MySQL B+Tree 更像每个字的页码，精确定位到行，索引本身更重。

4. 若改成逐行执行，瓶颈会从磁盘换成什么？

换成 CPU。一行一指令，没有 SIMD 批算；再把列块拆成行对象，解释和分支开销会把 CPU 打满。「零拷贝」不是正式术语，记成尽量按列块处理、避免物化为行对象，不是 Linux sendfile。

5. 为什么爱宽表、不太爱复杂 JOIN？

分片加算力、数据本地算。跨分片 JOIN 要把行在节点间拉来拉去，挡。宽表把常用维度预先铺在同一行，查询少跨节点关联。
