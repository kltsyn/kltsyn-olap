同一条查询里，压缩和跳数各自干了什么

口诀里的「跳数 / 布隆」不要读成一件事：跳数索引是总称；minmax 和布隆是其中两种 TYPE。稀疏主键也在跳 granule，但是目录，不是跳数索引。

表 ads_click：1 天 1 亿行，80 列，主键 (date, slot_id)，granule 默认约 8192 行（启用自适应粒度时还受 index_granularity_bytes 影响）。查询只要昨天、广告位 1001、计划 99 的费用合计。

FROM ads_click
WHERE date = '2026-10-11'
  AND slot_id = 1001

生效原理：跳数索引是总称，minmax/布隆是其中两种 TYPE

跳数索引 ≠ minmax/布隆。 INDEX … TYPE … 这一类东西叫 data skipping index（跳数索引）。minmax、bloom_filter、set、tokenbf_v1、ngrambf_v1 都是它的 TYPE（不同 ClickHouse 版本支持范围不同）。不管哪种 TYPE，干的都是同一件事：对每一块先做一次廉价判断，能证明「这块不可能命中 WHERE」就整块扔掉，连 .bin 都不读。

稀疏主键也在扔 granule，但它是 ORDER BY 自带的章节目录，不是跳数索引。查询不带主键时，目录歇了，跳数索引的便利贴照样问。

差别只在「用什么证明」：minmax 用两个数做范围比较；布隆用几比特做成员证伪。主键裁剪的单位是 granule。跳数索引的过滤单位由 INDEX … GRANULARITY N 决定：一张贴覆盖 N 个 marks；N=1 时才近似对应一个 granule，N>1 时一次扔掉的是更大的一块。本页示例 N=1。

minmax / 布隆都不是 SELECT 时扫全列现算的。建表写下 INDEX，INSERT 写 part（以及 merge 出新 part）时按块统计，结果放进很小的旁路文件 skp_idx_*.idx。查询会按需读取/利用这份跳数索引和稀疏主键的 primary.idx（可能走缓存，新版本也可能流式读，不保证一次性完整载入），用来决定打不打开哪几块的列 .bin。用到的是这两份摘要，不是 80 列数据，也不是整张表。

1. 设置 建表或 ALTER ADD INDEX。ORDER BY 列不用再建。已有数据要 MATERIALIZE INDEX。

2. 计算（写路径） 每个跳数索引块扫那一列（本页 N=1，约一个 granule）：minmax 记下两个数；布隆把值哈希进 bitmap。写 skp_idx_*.idx。

CREATE TABLE ads_click
(
    date Date,
    slot_id UInt32,
    campaign_id UInt32,
    user_id UInt64,
    fee Float64,
    INDEX idx_campaign campaign_id TYPE minmax GRANULARITY 1,
    INDEX idx_user     user_id     TYPE bloom_filter(0.01) GRANULARITY 1
)
ENGINE = MergeTree
PARTITION BY date
ORDER BY (date, slot_id)
SETTINGS index_granularity = 8192;  -- 默认约 8192 行/叠；自适应还看 index_granularity_bytes

-- 已有表：
-- ALTER TABLE ads_click ADD INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 1;
-- ALTER TABLE ads_click MATERIALIZE INDEX idx_user;
参数 含义
GRANULARITY 1 一张便利贴覆盖 1 个 mark，约等于一个数据 granule。N>1 时一张贴覆盖多个 marks，过滤单位变大
index_granularity = 8192 数据 granule 默认约 8192 行；启用自适应粒度时还受 index_granularity_bytes 约束
bloom_filter(0.01) 期望误报率约 1%。越小图越大。说「不在」可跳；说「可能在」仍要读盘
ORDER BY (date, slot_id) 稀疏主键自带跳数，这两列不必再 INDEX

同样在写 part 时算。每个跳数索引块不是存 min/max，而是把这块里的 user_id（本页 GRANULARITY 1，默认约 8192 个）哈希进一张小 bitmap。

怎么选

先分家：稀疏主键不是 INDEX。跳数索引是总称。下面选的是跳数索引的 TYPE。本页示例 GRANULARITY 1，过滤单位约等于一叠 granule；N>1 时一张贴覆盖多个 marks。选哪种，只看哪套测试更容易把整块证伪。收益高度依赖数据相关性和查询谓词。

列的样子 用什么 为什么
已在 ORDER BY 里：date、slot_id 不用跳数索引 稀疏主键（目录）已经在跳，不是 INDEX
一段行里比较扎堆：campaign_id、状态码 跳数索引 TYPE minmax 两个数就能证伪整叠
高基、几乎随机：user_id、device_id 跳数索引 TYPE bloom_filter(0.01) minmax 会变成 1～很大，跳不动
低基枚举：状态、类型码 跳数索引 TYPE set 这叠出现过的值做集合，比 minmax 更贴
字符串子串：LIKE '%x%' 跳数索引 TYPE tokenbf_v1 / ngrambf_v1（版本支持范围不同） 整值布隆吃不了子串

数字是教学用量级（1 亿行、granule 默认约 8192、本页 INDEX GRANULARITY 1、20 个主键命中、2～3 个 campaign 命中），用来对齐机制，不是一次真实 benchmark。
